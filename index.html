<HarnessPAI/>: An evolvingharness for physical AI

Evolving executable code integrates perception, reasoning, and action,
and feeds successful trajectories back into model training.

Start with a contradiction rather than a leaderboard: the robot can grasp and transport objects, yet changing a sentence or moving a plate can make the task fail. What is missing?

The talk moves from observed failures to the motivation for a harness, then explains why code and two timescales are useful. Section 4 evaluates both the execution framework and the model improvements obtained by feeding successful trajectories back into supervised fine-tuning. Allow about 40–45 minutes for the talk; the concluding slides summarize the takeaways and future directions, followed by a contact page.

Open-loop at the program level

Ground → act → verify → proceed

  • Sensors and low-level feedback remain active.

BETWEEN ROLLOUTS

Closed-loop evolution

Execute → diagnose → revise → validate

  • Use traces, outcomes, and rollout videos.
  • Edit an isolated candidate program.
  • Promote code only after validation.

The program changes between attempts; observations and checks guide execution within each attempt.

Open-loop is a program-level definition: no high-level rewriting or deliberative replanning is required during a rollout. It does not mean open-loop motor control or blindness to current observations.

Closed-loop evolution uses feedback from multiple rollouts to revise the executable program. Experimental resets permit development trials, but reset availability should not be assumed in deployment. This separation is central to interpreting the framework.

The contract fixes what success means before code evolution begins.

The contract states evaluation scope, authoritative goal conditions, graph terminal state, and signals that do not suffice for success: clean exit, terminal code state, high dense reward, and the writer’s own convergence claim.

Stronger action models and better executable harnesses are complementary.

The first takeaway is the system-level contribution: an action model remains a useful primitive, while code organizes perception, task reasoning, physical actions, and verification. Behavioral perturbation results motivate this organization without proving that training destroyed vision or language.

The second takeaway is the separation of timescales. Open-loop refers to the fixed program within each rollout; observations, feedback control, and predefined checks remain available. Closed-loop evolution edits candidate code between rollouts and retains reusable repairs at workflow nodes.

The third takeaway is data feedback. A converged program supplies successful observation–action trajectories for perturbed tasks without new human demonstrations for those collected variants. The paper evaluates supervised fine-tuning of standalone VLA and WAM models, not alternating harness–model co-evolution.

The execution gains are percentage-point differences against the same frozen backends: LIBERO-PRO 34.9% to 96.5%, and RoboCasa WorldDreamer 65.0% to 92.2%. The separate post-training gains are π0.5-LIBERO 34.9% to 73.7%, and DreamZero Object Swap / Task mean 5.1% to 26.5%. Their protocols differ; the latter are model improvements rather than harness-plus-fine-tuned-model evaluations. LIBERO / PRO includes development seeds, and DreamZero feedback covers Object only.

01

Standardize atomic-action interfaces

Give PPO, VLA, and WAM primitives a shared instruction-to-action contract
so the harness can compose stronger backends through a uniform interface.

02

Use scene models to stabilize perception

Explore maps, persistent scene models, and real-to-sim transfer
to reduce repeated grounding cost and improve reliability.

03

Combine coding agents with reusable program packages

Retrieve or lightly adapt validated code for familiar subtasks;
reserve high-level reasoning for novel situations in long-horizon tasks.

04

Explore alternating harness–model improvement

Fine-tune on successful trajectories, then re-evolve the harness around the improved model;
test whether successive cycles yield further gains.

Proposed directions beyond the experiments reported in this paper

The first three directions follow the paper’s dedicated Future Work section. They are proposals rather than evaluated extensions: a uniform atomic-action contract across PPO/VLA/WAM, persistent mapping or scene models including real-to-sim transfer, and cooperation between a coding agent’s open-ended reasoning and validated code packages.

Standardizing a contract is a research direction, not a claim that arbitrary current policies already implement compatible interfaces. Scene modeling seeks cheaper and more stable grounding rather than removing all current observations or feedback. Reusing programs for familiar subtasks leaves the agent to reason about genuinely novel situations.

The fourth direction is explicitly suggested in §4.5: wrap the harness around the fine-tuned model and iterate. This would alternate model learning and harness re-evolution. The present work evaluates only one-way harness-to-model feedback, so the new cycle is future work and has no reported success rate or convergence guarantee.

Validation should continue to separate development success, unseen-scene transfer, and adaptation on previously failed evaluation seeds. Any improvement should be established through task-appropriate metrics and independent success checks rather than a coding agent’s own convergence claim.
