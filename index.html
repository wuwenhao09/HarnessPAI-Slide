<HarnessPAI/>: An evolvingharness for physical AI

Evolving executable code integrates perception, reasoning, and action,
and feeds successful trajectories back into model training.

Start with a contradiction rather than a leaderboard: the robot can grasp and transport objects, yet changing a sentence or moving a plate can make the task fail. What is missing?

The talk moves from observed failures to the motivation for a harness, then explains why code and two timescales are useful. Section 4 evaluates both the execution framework and the model improvements obtained by feeding successful trajectories back into supervised fine-tuning. Allow about 40–45 minutes for the main talk; the last three slides are discussion material.

Precondition: useful primitives already exist. A harness cannot create a capability absent from both the model and available control APIs.

“Unlocking” is not a mysterious prompting trick. It means establishing the correct target, invoking a competent primitive at the right stage, and checking its result.

If neither the model nor the control API can grasp an object, rearranging calls cannot manufacture a grasping capability. We will return to this boundary at the end.

task_program.py Illustrative pseudocode
def execute(instruction, robot, action_model):
    scene = perceive(robot.observe())
    target = ground(instruction, scene)
    destination = locate_destination(scene)

    robot.approach(target.pose)
    action_model.grasp(target)
    if not verify_grasp(robot.observe()):
        return safe_stop()

    robot.transport(destination)
    action_model.place(destination)
    return verify_goal(robot.observe())

Press V. This clip gives the physical motivation for separating execution from program revision. Once a pot falls below the table, another reasoning step cannot simply restore the previous state. The failure is not universally irreversible under all possible interventions, but it can be unrecoverable within the task and its available controls.

Describe the source accurately: the left is an illustrative scripted drop in robosuite TwoArmLift; the right is a successful HarnessPAI lift. This is not evidence that a particular WAM failed in RoboCasa, nor a quantitative success-rate comparison.

Why call the response open-loop? At the program level, the validated task logic stays fixed during a rollout. It still reads sensors, checks grasps, uses feedback control, and may run predefined recovery or stop. Irreversibility motivates preventive checks and first-attempt reliability; it does not prove open-loop control is universally safer.

Programs improve between trials in a resettable development environment. Do not assume that the same resets are available in real deployment.

A physical mistake cannot always be fixed by undoing a line of code.

Follow the video with the design principle. A stable, inspectable program provides explicit checks before committing to risky stages. High-level code revisions occur between runs.

This is program-level open-loop execution, not sensor-level open-loop control. The claim is not that removing feedback prevents accidents. The combination of explicit grounding, checks, and validated programs aims to reduce error risk.

Evolution uses resettable experimental environments. A real robot may not be able to reset, and the program is not a formal safety proof.

Key distinctionProgram-level open-loop ≠ blind action replay. Cross-rollout evolution ≠ continuous online LLM replanning.

This is the central technical distinction. Within a rollout, what is fixed is the program—not action values or sensor inputs, and not the outcome of conditional branches. A fixed program can implement feedback control using fresh observations.

Across rollouts, execution evidence changes the program from Pk to Pk+1. These are logical timescales—execution versus improvement—not specific millisecond or second sampling rates.

Action parameters remain frozen in the main evolution loop. The later fine-tuning study is a separate data-feedback experiment.

Favorable conditions

  • Useful atomic model or control primitives.
  • Observable, checkable intermediate stages.
  • Repeated tasks that allow program reuse.
  • Controlled trials during development.

Remaining boundaries

  • Organization cannot create absent skills.
  • Opaque long-horizon stages are harder to repair.
  • Fixed code and checks are not a safety proof.
  • Different protocols are not controlled ablations.
Open questions: unseen-scene generalization, cheaper evolution, and adaptation under explicit safety constraints.
